# Решение

## Затраченное время

Время разработки и отдельно время настройки окружения:
* Настройка окружения - всё настроено хорошо в Initial, настраивать окружение не пришлось;
* Добавил интервальный polling в Vite, чтобы не перезагружать контейнеры при обновлении фронтенда - примерно 3 минуты;
* Старые данные при переключении - примерно 15 минут;
* Ошибка при загрузке данных о заявке с отсутствующим источником - примерно 5 минут;
* Неавторизованный доступ к изменению статуса заявок - примерно 15 минут;

## Найденные причины

Для каждой проблемы: воспроизведение → причина → исправление → проверка.
* Старые данные при переключении:
  * Воспроизведение - быстро переключался между карточками заявок
  * Причина - "висящие" вызовы к API, т.е. те, которые выполнялись даже несмотря на переключение на другую заявку;
  * Исправление - добавление контроллера прерывания (AbortController) в опции fetch позволяет прервать запрос при изменении выбранной заявки;
  * Проверка - быстрое переключение между карточками заявок больше не загружает старые данные;
* Ошибка при загрузке данных о заявке с отсутствующим источником;
  * Воспроизведение - открыл заявку №103 без источника;
  * Причина: исключение на стороне сервера - внедрение данных об источнике без проверки на их наличие:
  ```text
    api-1  | [1] [Mon Oct 12 04:56:49 2026] ErrorException: Trying to access array offset on value of type bool in /app/src/TicketRepository.php:25
    api-1  | Stack trace:
    api-1  | #0 /app/src/TicketRepository.php(25): {closure}(2, 'Trying to acces...', '/app/src/Ticket...', 25)
    api-1  | #1 /app/src/routes.php(44): TicketRepository->find(103)
    api-1  | #2 /app/public/router.php(4): require('/app/src/routes...')
    api-1  | #3 {main}
  ```
  * Исправление - добавление проверки на наличие данных об источнике и, если данных нет, не включать их в массив данных о заявке;
* Неавторизованный доступ к изменению статуса заявок;
  * Воспроизведение - войдя в учётную запись без права на изменение статуса заявок, программно обратился к API:
  ```ts
  const $1 = await fetch("/api/tickets/102/source", {method: "POST", body: JSON.stringify({"source_id": 1}), headers: {"X-CSRF-Token": "..."}});
  ```
  * Причина - отсутствие проверки прав на API Route изменения данных о статусе заявки;
  * Исправление - добавление проверки прав при обращении к Route;
  * Проверка - вызов сниппета выше теперь не позволяет изменить статус заявки неавторизованных на это пользователей;

## Решения и компромиссы

Для решения проблем существует множество способов решения, однако для последних двух (Ошибка при загрузке данных о заявке с отсутствующим источником, Неавторизованный доступ к изменению статуса заявок)
решения простые и приходят на ум сразу - отсутствуют данные о статусе = не нужно обращаться к отсутствующим данным; нет проверки на право изменения - нужно добавить.
В первой (Старые данные при переключении) можно было бы воспользоваться простым булевым флагом, но, поскольку API браузера уже предоставляет AbortController,
было решено воспользоваться именно им, ведь `fetch()` принимает его в качестве опции из коробки.

## Оставшиеся ограничения

Что не закончено и что сделали бы следующим?
Я бы:
* Перенёс проверки на право доступа внутрь каждого кода Route, поскольку текущие проверки на корневом уровне
несут каскадный характер - любой Route, объявленный ниже проверки на право, будет требовать такое право, хотя
в будущем могут потребоваться более точные проверки на права (например, если создать 2 группы пользователей -
те, кто создают новые источники заявок и те, кто их редактирует - при каскадной проверке это сделать невозможно).
* Сделал preg-группы в URL именованными (https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Regular_expressions/Named_capturing_group),
так можно будет менять параметры в URL местами, не беспокоясь за их индексы - сейчас параметры жестко привязаны к индексам.
* Вынес код TicketPanel в хук(и).
* Использовал бы какую-нибудь библиотеку или фреймворк для Route-инга, это бы сильно упростило код, а также,
если выбранный инструмент это позволял, перенёс бы проверку прав туда (например, Middleware/Proxy/Gate)
* Перешёл на TypeScript для лучшей безопасности типов и строгого статического анализа.
* Использовал бы React 19's `<Suspense>` в местах отображения данных с API, чтобы избежать использования булевых флажков, типа `loading` в `TicketPanel.jsx`
* Использовал бы ORM (понимаю, что это учебное задание, и оно сильно упрощено,
но я хочу его воспринимать, как реальный проект, поэтому такие крупные изменения, конечно, стоит делать ещё на этапе проектирования).
Вытекающее отсюда - файлы миграции с поддержкой отката и изменения.
* Использовал бы Sass и модульные стили для каждого компонента
* Разделил бы страницу заявок на компоненты

Таких изменений много, это первое, что пришло на ум. Можно найти и ещё, если подумать подольше, но, думаю, это уже
будут изменения на развитие, фичи для улучшения продукта.
